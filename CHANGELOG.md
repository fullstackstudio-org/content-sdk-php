# Changelog

## 0.32.0 (not yet tagged)

- The visitor's language in the shop and the chat, `fsc:doctor`, documentation and the example site (multilanguage plan, task 23, batch 3). Same rule as batch 2 (the call's own `$options['locale']` wins, else the client's content language on a project with two or more enabled languages and only an enabled language; otherwise nothing is sent, so a single-language request is byte-identical, tested per call). Reads: `cart->shippingOptions()`, `products->categories()` and `chat->config()` send `?locale=` (the answers have `locale` and `availableLocales`). Writes: `cart->applyCode()` (the discount validation), `orders->place()` and `chat->open()` put `locale` in the body (an own `locale` in the input wins; the widget's own language still wins in `chat->open()`). `fsc:doctor --online` warns (`LET OP`) when the project is multilingual and the site never sets a content language (the SDK's own pages count as setting it; a site with own routes needs `Content::setLocale()`, `Content::withLocale()` or a `'locale' =>` read option in its PHP files or views; `config/` is not searched). AGENTS.md has the new section "Meertalige teksten" (what the Hub translates, the read rule, `Content::setLocale`, option labels, `?lang`, the event `pathTemplate` for the sitemap). `examples/laravel` shows the contact page in two languages (`/contact`, `/en/contact`, `ContactController`), its own strings under `resources/lang` (namespace `site`), a language switch and localized nav and footer links; its form and its cookie banner come in the language of the page (`ExampleSiteMultilingualTest` renders both languages and a single-language project). Behaviour change: none on a single-language project; on a multilingual one shipping options, discount labels, categories, orders and the chat now come in the visitor's language.

- The visitor's language in the modules (multilanguage plan, task 16, batch 2). `ModuleContext` now asks its client for the content language (`localeQuery()`, `bodyWithLocale()`), with the rule of batch 1: the call's own `$options['locale']` wins, otherwise the client's language when the project has two or more enabled languages and the language is enabled, otherwise nothing is sent (no project read either while no language is set). Reads: `events->list()`, `events->get()`, `appointments->services()`, `service()`, `bookingPageUrl()`, `newsletter->lists->list()` and `get()` send `?locale=` (cache keys follow the URL, so each language has its own entry; the same webhook tags clear them). Writes: `events->register()`, `appointments->book()`, `newsletter->subscribe()`, `members->register()` (the `locale` key now passes the input whitelist) and `tickets->create()` (also in the multipart `data` part) add `locale` to the body, after the caller's own fields; a `locale` in the input wins, then `$options['locale']`, then the client's language. Single-language projects, a language that is not enabled and a client without a language send exactly the old URL and body (tested per call). `ContentClient::withLocale()` no longer clones: a copy is a new client on the same transport and cache with its own modules, because the modules' context points back at its client (the original keeps its language). `Content::urls()` gets `visitorLink($url, $locale)` (adds `lang=` for a non-default enabled language, replaces an own `lang`, keeps the fragment; nothing else changes) and `localize($path, $locale)` (locale prefix only); `Urls::event($event, $locale = null)` takes a language and `content.links.event` may hold `{locale}` (`PathResolver` takes the language from the path and reads the event in it; an event under a locale prefix is read in that language). The resolved event keeps `locale` and `availableLocales`. `<x-content::head />` prints hreflang on an event page from `availableLocales` (new `Alternates::forEvent()`). The `eventList`, `event` and `appointmentBooking` blocks read in the visitor's language, link the Hub pages with `?lang=` and the site's own event and booking links with the locale prefix (or `{locale}`); the `newsletterSignup` block carries `_fsc_locale` on a multilingual page and `NewsletterController` subscribes in it (only an enabled language). Behaviour change: none on a single-language project; on a multilingual one the visitor now gets event, service and list texts, links and mails in their own language.

- Page builder v2, found on the real stack (task 20). Three fixes in `preview.js`, all only in a portal preview:
  - The layouts a block supports were never read: the markup prints `data-fsc-layouts` comma separated (`overlay,image-right,image-left`) and the script split on white space, so every block reported no layouts and the portal hid the layout choice for default views. It now accepts commas and white space (the test fixture had used a space, which hid it).
  - An inline `<style>` between the blocks (`blocks.css`) is no longer swapped for a copy on every refresh when the answer carries a new CSP nonce. The Hub fallback (nonce CSP, new nonce per answer) lost all block CSS after the first edit; a changed inline style now gets the page's own nonce. Signatures are compared without `nonce`.
  - The hover message to the portal goes out at once when nothing was sent in the last 60 ms (leading edge), then at most every 60 ms with the latest value; the outline row in the portal followed the pointer 60 ms late.
Payments as a global module, step 3.2 (plan payments-global). A minor bump: only new methods and new optional arguments; every existing signature and behaviour is unchanged. `ContentClient::VERSION` moves to `0.32.0` when this is tagged; it is not published or tagged before the Hub batch that serves the routes is released. Needs a Hub with `GET /api/v1/payments/methods` and the `method` parameter on the start routes; an older Hub answers 404 on `methods()` and rejects `method` with 400, so only use them after the Hub is updated.

- **`payments->methods(array $options = [], ?string $source = null)`**: `[{id, label}]`, exactly the payment methods a start would accept (the provider is not named). `$source` (`order`, `invoice`, `appointment`, `form_submission` or `event_registration`) asks for the provider that payments of that kind are routed to; without it the answer is for the project's default provider (Hub lead decision after the payments batch 3 review: no longer the union of every connection, which a start could then refuse). Never cached. Show the labels to the buyer, send the chosen `id` back as `method`.
- **`payments->list(array $params = [])`**: all payments of the project over every source, newest first (`payments`, `page`, `limit`, `total`); filters `status`, `subject`, `view`, `from`, `to`, `q`, `page`, `limit`. Never names the payer.
- **`payments->start($input, $options, ?string $method = null)`** and **`payments->startForOrder($order, $options, ?string $method = null)`**: the new optional last argument is the chosen method id. An id the connection that would take the payment does not offer is a `ContentException` with `errorCode()` `payment_method_unavailable` (HTTP 409), before anything is created; call `methods()` again and let the buyer choose again. Without `$method` the request is byte for byte what it was.

## 0.31.0 (not yet tagged)

Page builder v2 and the out of the box site (0.29 and 0.30 were never tagged on their own; their entries follow). What a site owner or builder needs to know:

- **Page builder in the portal.** Needs SDK 0.31 on the site for the full editor: the real site is the canvas (selection, reordering, typing headings and rich text on the page, layouts and tones). `preview.js` speaks canvas protocol 2 (`ready {proto: 2, caps}`, answered by the portal's `init`); the classic editor (protocol 1) keeps working as in 0.28. Nothing to configure: the preview is on with a server token. `php artisan fsc:doctor` checks it (see below).
- **F6 in the page builder.** `preview.js` forwards F6 and Shift+F6 pressed in the site frame to the portal as `shortcut {name: 'pane-next'}` and `'pane-prev'` (plain F6 only, not with Ctrl, Alt or Meta, not during IME composition; the browser's own F6 is prevented), so the focus can move on from the canvas to the next pane of the builder.
- **Layouts and tones.** Every block can carry `layout` and `tone`. Default views implement all of them; a site view opts in with `content.block_layouts.<type>` and `$look`. See AGENTS.md, A19 ("Eigen blokview in de bouwer"), and `examples/laravel` (`resources/views/blocks/cta.blade.php`).
- **Doctor.** New section lines for the canvas (`FOUT` when the preview script route, the preview middleware or `preview.js` is missing; `LET OP` for a changed `FSC_PREVIEW_PATH`) and for layouts (`LET OP` when a site view exists for a type with layouts and `content.block_layouts` has no entry for it, or names a type or layout the SDK does not know; `INFO` for a site view without `$edit` markers).
- **Upgrading from 0.28 to 0.31.** Replace nothing: pages, views and config keep working. To make a site view part of the builder add `'<type>' => [...]` to `content.block_layouts`, print `$look` on the root of the block and mark typeable fields with `{!! $edit('field') !!}`; a site view that does none of this is still selectable and editable in the settings pane, just without layouts and typing on the page. Run `php artisan route:clear` once after updating a site that uses `route:cache` (the preview script route `content.preview.script` must exist; `fsc:doctor` says so when it does not).
- **Below 0.31 the builder has less to work with.** Sites on 0.27 to 0.30 get the real site as canvas with click selection only (protocol 1; no layouts, no typing on the page). Sites below 0.27, or whose preview does not answer within 5 seconds, get the Hub's fallback renderer (neutral style, the SDK's own blocks, no layouts offered). The placeholders for incomplete blocks (a labelled box for a block whose required choice is not made yet, the `fscPlaceholder` view) are drawn from 0.31 on and by the Hub's fallback: on a site below 0.31 an incomplete block is left out of the page itself (the site has no view for a placeholder and skips it), so it cannot be selected there (use the block list); once the portal switched such a site to the fallback, the placeholder shows. Upgrade the site to 0.31 to get them on the real site.
- **Not changed for visitors.** A live page renders byte for byte as before for a block without `layout` or `tone`; every builder marker (`data-fsc-edit`, wrapper data attributes, placeholders) is printed in a portal preview only.

- Page builder v2, rich text typed on the page (task 16; only in a portal preview, a live page is unchanged). `ready.caps` adds `edit-rich` and `format`. A rich field (`data-fsc-edit-kind="rich"`: richText `html`, `columns.N.html`) becomes editable only when the portal's `init` also says `rich: true`, so a portal that cannot take rich text yet never loses what was typed. - `Analytics::csp()`/`mergeCsp()` and `Content::analyticsCsp()`/`analyticsCspMerge()` for the Content-Security-Policy.
- Forms: `<x-content::form>` sends the first-touch attribution as `_meta` (`Forms::attributionMeta()` for your own forms).
- Redirects keep the utm and ad click id parameters also when the target has its own query or is absolute.
- Error monitoring (GlitchTip) for the Content module `errors`: the DSNs come from Content (`GET /api/v1/project/errors`, cached 10 minutes, the last good
  answer survives an outage). Backend exceptions are reported through Laravel's exception handler (`reportable`), after the response; the browser reporter
  is `<x-content::errors />` with `GET /_fsc/e/reporter.js` and the first-party tunnel `POST /_fsc/e/envelope`. Events are rebuilt from an allowlist, messages
  go through the scrubber of fss-core (shared test vectors). No new dependencies (a minimal envelope sender instead of sentry-laravel). See AGENTS.md.

## 0.5.1

- `submitForm` leaves out an empty list, like the JS SDK (an optional file field without files no longer breaks a multipart request; in JSON
  the field is no longer sent as `[]`).
- Multipart: field and file names lose quotes, backslashes and every control character, so a name can never end its header parameter or line.
- Example image (`examples/laravel`): uploads were capped at 2 MB. The limit is now `FSC_UPLOAD_MAX_MB` (default 20, 1-55) and sets nginx
  `client_max_body_size`, PHP `upload_max_filesize`/`post_max_size` and `memory_limit` together.

## 0.5.0

- Hardening: the Laravel `FormController` no longer drops uploads that PHP rejected (`UPLOAD_ERR_*`, new `Forms::uploadErrors()`): size errors give the `fileTooLarge` label, other errors
  the general error, and a POST emptied by `post_max_size` is never submitted. `Request::multipartBody()` strips `\` from file names and falls back to `application/octet-stream`
  for a content type that is not a plain `type/subtype`.
- Form file uploads. `submitForm` accepts `SplFileInfo` (incl. Laravel/Symfony `UploadedFile`), `Http\UploadFile` or a list of them as the value of a `file`
  field and then sends `multipart/form-data` (text parts, `_meta` as JSON, repeated file parts); without files the request is unchanged JSON.
  New `downloadSubmissionFile($formKey, $submissionId, $fileId)` (server token) returns the bytes, content type and file name.
- `CurlTransport` now builds the multipart body with the same encoder as `Psr18Transport` (`Request::multipartBody()`) instead of `CURLStringFile`.
- Laravel: `FormController` forwards the uploads of the form's file fields (413/415 give a message), and `<x-content::form>` renders `type="file"`
  (`accept`, `name[]` + `multiple`, `enctype`). New helpers `Forms::acceptAttribute()`, `Forms::hasFileField()`; `Forms::values()` takes the uploaded files as a third argument.
